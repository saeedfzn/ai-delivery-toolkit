Reusable AI tooling for delivery teams

Skills, an MCP server, evals and a usage dashboard for the teams on Project Lantern, a fictional public-sector digital programme. Everything on this page is produced by code in the repository, and every part has tests that run in GitHub Actions.

What is in the toolkit

5 Claude Code skills

User stories, PR review, release notes, meeting notes to ticket drafts, WCAG 2.2 quick check. Each one flags missing information and never invents ticket numbers. Loadable as one plugin.

Skill evals

Five cases with a trap in each, run through a real model and graded by code: no invented keys, no personal data, required structure. See the latest run.

MCP server

TypeScript, official MCP SDK, 30 tests. Six read-only tools with zod validation; the one "write" tool returns a draft for a person to approve.

Jira and Confluence

The same tools read from Jira Cloud and Confluence Cloud over REST when credentials are set. GET requests only, responses validated, assignees pseudonymised.

Skill evals

Each skill is run against a fixed request with a trap in it, and the output is graded by code. The graders check the guardrails the skills promise: no ticket key that was not in the input, no personal data carried over, the agreed structure present, and no claims the skill is told never to make.

Loading results...

An earlier run scored 19 of 20: pr-review-checklist raised a hard-coded API key as a blocker but quoted its value in the review. The skill gained a guardrail and the case now passes. Results are in evals/results/latest.json with the graded outputs beside it; CI re-grades them on every push. Run python -m evals.run_evals --live to repeat it with a model.

Skills catalogue

Claude Code skills live in skills/<name>/SKILL.md. Copy a folder into .claude/skills/ in your repo (or ~/.claude/skills/ for yourself) and Claude uses it when your request matches its description. Or load all five for one session with claude --plugin-dir .

user-story-writer

Rough request in, user stories with Given/When/Then acceptance criteria out. Splits by user outcome, always covers an unhappy path, adds an accessibility criterion for UI.

Guardrails: no invented keys, points or owners (TBC instead); open questions listed separately; personal data replaced with roles.

pr-review-checklist

Reviews a PR or diff against a checklist covering size, correctness, tests, security, accessibility and docs. Returns a verdict plus ranked blockers, should-fix items and at most three nits.

Guardrails: never claims a test passed unless it ran; secrets or personal data are always a blocker; posts nothing unless asked.

release-notes-drafter

Groups git log output with a small tested Python helper, then writes notes for the team or for service users. Every bullet traces back to a commit.

Guardrails: ticket keys only if they appear in the commits; no author names; no notes for an empty range.

meeting-notes-to-jira

Notes in, decisions, actions and open questions out. Searches the backlog for duplicates through the MCP server, then drafts tickets for approval.

Guardrails: never creates tickets; never turns an idea into a decision; flags empty sections in the notes.

wcag-quick-check

An automated scan (missing lang, alt, labels, empty links, heading skips, positive tabindex, autocomplete) plus a manual checklist of WCAG 2.2 AA items a script cannot judge.

Guardrails: never says a page "is compliant"; prefers native HTML to ARIA; names the success criterion for every issue.

Prompt library

Five copy-and-fill prompts in prompts/: sprint status update, test cases from acceptance criteria, code handover note, plain English rewrite, RAID log entry. Each has when-to-use, inputs and an example.

MCP server: lantern-delivery

Gives Claude read access to the programme's tickets and pages through the Model Context Protocol, so answers come from the data rather than from memory. By default the data is mock JSON. Set ATLASSIAN_BASE_URL, ATLASSIAN_EMAIL, ATLASSIAN_API_TOKEN and JIRA_JQL and the same six tools read from Jira Cloud REST v3 and Confluence Cloud REST v2, with GET requests only.

ToolWhat it does
search_ticketsFilter by words, status, team, sprint, label
get_ticketOne ticket in full, by key
search_pagesSearch pages, returns snippets
get_pageOne page in full, by id
summarise_sprint_statusPoints, status counts, blockers, computed in code
draft_ticketReturns a draft for approval; redacts personal data; creates nothing
 
cd mcp-server
npm ci && npm test && npm run build
npm run proof    # raw JSON-RPC over stdio: initialize, tools/list, tools/call
claude mcp add lantern-delivery -- node "$(pwd)/dist/index.js"

Every tool call writes one JSON line to stderr with the tool name, outcome, duration and response size, and never the arguments, so usage and latency can be reported without logging what people asked.

Get started in 10 minutes

You need Git, Node.js 22.12 or later, Python 3.10 or later, and Claude Code signed in. On Windows, use py -3 in place of python.

  1. Clone the repo 1 min
    git clone https://github.com/saeedfzn/ai-delivery-toolkit.git && cd ai-delivery-toolkit
  2. Add the skills to your project 1 min
    Copy the folders you want from skills/ into your repo's .claude/skills/. Start with user-story-writer and pr-review-checklist.
  3. Build and register the MCP server 3 min
    cd mcp-server && npm ci && npm run build, then the claude mcp add command above. Check it with claude mcp list.
  4. Try it 3 min
    In Claude Code, ask: "Summarise Sprint 15 status and list what is blocked." Then: "Write a story for caseworkers who want to filter their queue." Watch for the open questions it raises.
  5. Check the guardrails 1 min
    Ask for "ticket LNT-999". It should say the ticket does not exist instead of making one up.
  6. See your usage 1 min
    python scripts/usage_report.py data/usage-log.jsonl prints the metrics this page charts.

Rules that apply everywhere: no personal data, secrets or live case data in prompts; a person reviews every output before it is used; record which skill you used in your PR description.

45-minute workshop: AI skills for delivery teams

For a delivery team of up to 12 (developers, testers, BAs, delivery managers). Everyone needs a laptop with Claude Code installed; the facilitator shares a screen. Full facilitator notes are in docs/workshop-45-min.md.

TimeActivity
0-5Why skills, not one-off prompts. Show the adoption chart: skill outputs are accepted as-is more often than ad hoc prompts.
5-15Live demo. Messy meeting notes become decisions, actions and ticket drafts via meeting-notes-to-jira and the MCP server. Point out the open questions and the draft-only rule.
15-30Hands-on in pairs. Each pair picks a skill and runs it on a provided synthetic input. Note one thing it did well and one thing it got wrong.
30-38Break the guardrails. Pairs try to get the skill to invent a ticket key or keep personal data. Share what happened.
38-43Improve a skill. Turn one finding into a change to a SKILL.md and a new eval case, and outline the pull request (see CONTRIBUTING.md).
43-45Close. One action each: which skill will you use this week? Usage shows up in next week's report.
